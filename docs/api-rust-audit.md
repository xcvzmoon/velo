# API workspace Rust audit

This audit covers the Rust changes for [issue #21](https://github.com/xcvzmoon/velo/issues/21). It applies Microsoft's [Pragmatic Rust Guidelines](https://microsoft.github.io/rust-guidelines/guidelines/checklist/index.html), version 2026.6, to the collection, functional request, authentication, desktop orchestration, and persistence boundaries.

## Findings and fixes

| Guideline                       | Finding                                                                                        | Applied change                                                                                                                                                                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-PUBLIC-DEBUG                  | Collection documents, session state, and responses can contain credentials or private content. | Public types implement `Debug`; content-bearing types omit their content. Integration tests check sensitive output.                                                                                                                     |
| M-STRONG-TYPES                  | API-key placement and functional outcomes need explicit states.                                | Shared authentication uses a header/query enum. Functional outcomes distinguish passed, failed, cancelled, and skipped steps.                                                                                                           |
| M-BALANCED-MODULES              | Collections and interactive execution have different ownership and persistence rules.          | Collection models, functional transport, desktop orchestration, OAuth, and API history have separate modules. Existing transport, extraction, assertion, and dataset implementations remain shared.                                     |
| M-PANIC-IS-STOP                 | Invalid documents, files, credentials, or responses must not panic.                            | Boundaries return stable error codes without request values. Blocking-task programming panics propagate to the application's existing panic policy.                                                                                     |
| M-YIELD-POINTS                  | Sequential collection execution and cancellation must cooperate with the runtime.              | Request and delay waits are asynchronous. Cancellation prevents later steps and awaits owned upload cleanup. OAuth cancellation closes its owned callback task and listener.                                                            |
| M-INITIAL-CAPACITY              | Large collection defaults can multiply when inherited by many requests.                        | Merged request definitions have an aggregate 8 MiB limit; entry depth/count, resolved data, step count, retained evidence, sessions, and history also have explicit limits.                                                             |
| M-FFI-TRANSLATES                | Functional and load requests must not diverge at the desktop boundary.                         | Engine APIs own validation, HTTP transport, body inspection, assertions, extraction, cookies, and deterministic dataset allocation. Desktop commands enforce authorization, execution admission, OS credentials, and local persistence. |
| M-STATIC-VERIFICATION           | Type checking alone cannot prove traffic ordering, redaction, or cancellation.                 | Local HTTP integration tests exercise the engine and real Tauri IPC. Additional tests cover portable collections, storage reopening, history retention, and OAuth callbacks.                                                            |
| M-CANONICAL-DOCS / M-DOC-INLINE | New public APIs need discoverable contracts and examples.                                      | Engine exports have inline documentation, canonical arguments/returns/errors sections, and compiling doctests.                                                                                                                          |

No new unsafe Rust or panic recovery is introduced. The change retains the workspace's existing allocator and target settings; changing those application-wide policies is outside this feature.

## Security and resource checks

Collections preserve secret references and reject literal credentials in recognized sensitive fields, including inherited aliases. Portable copies remove local attachment paths. OAuth uses S256 PKCE, random verifier/state values, constant-time state comparison, a bounded loopback listener, HTTPS token endpoints, explicit refresh, and an atomic OS credential record bound to the token endpoint and client ID.

API sends and collection runs use the same desktop admission gate as load execution. Interactive cookie jars and extracted values stay in memory, isolated by collection and environment. Independent collection runs start fresh sessions. Reports redact known request/secret values, common JSON credential fields, configured JSON pointers, and sensitive headers before retention or export. Configured field masking withholds incomplete or invalid JSON rather than exporting an unmasked prefix.

History stores authored request snapshots with secret references for restoration. It omits session state and, by default, response bodies and headers. Disabling response persistence scrubs existing retained response content. Collection execution keeps at most 1 MiB of response content in one report, with explicit withholding markers after the limit.

## Verification and practical limits

Automated tests cover collection structure and ordering, inheritance, credential rejection, portable upload rebinding, deterministic functional requests, negative-status assertions, shared sessions and extraction, cancellation, redirects, unsupported response formats, resource admission, history retention, API-key authentication, and OAuth callback cleanup. The repository verification sequence is `pnpm check`, `pnpm typecheck`, `pnpm test`, then `pnpm build`. Additional checks include type-aware Oxlint, Clippy with warnings denied, generated binding consistency, and Rust documentation with warnings denied.

Live OAuth provider authorization, provider-specific consent behavior, and interactive OS credential prompts require real credentials and a configured provider. The automated callback tests do not claim to verify those external systems. The user guide documents the supported loopback callback and explicit token lifecycle.
