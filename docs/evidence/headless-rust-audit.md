# Headless runner Rust audit

Date: 2026-11-08. Scope: issue #18's CLI crate, shared report context, run outcome aggregation, report deserialization, and desktop call-site change.

The review uses Microsoft's [Pragmatic Rust Guidelines checklist](https://microsoft.github.io/rust-guidelines/guidelines/checklist/), especially [resilience](https://microsoft.github.io/rust-guidelines/guidelines/libs/resilience/), [correctness](https://microsoft.github.io/rust-guidelines/guidelines/correctness/), [performance](https://microsoft.github.io/rust-guidelines/guidelines/performance/), and [documentation](https://microsoft.github.io/rust-guidelines/guidelines/docs/). It covers the changed Rust code, not a repository-wide certification.

## Findings and fixes

| Guideline                                     | Finding                                                                                                                        | Final implementation                                                                                                                                                                                                                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-FFI-TRANSLATES, M-SMALLER-CRATES            | A desktop-hosted binary would couple CI to graphical packages and credential/storage lifecycle.                                | A sibling application crate depends only on engine/contracts and CLI infrastructure. Its normal dependency tree contains no Tauri, SQLite, or keyring.                                                                                                                                                        |
| M-SINGLE-ITEM-PATH, M-BALANCED-MODULES        | Copying desktop's report context would let comparison identity and privacy rules drift.                                        | The engine exports one content-free `report_configuration` function. Desktop and CLI call it; existing report formats and comparison formulas remain shared.                                                                                                                                                  |
| M-PANIC-IS-STOP, M-PANIC-CONTINUATION         | Treating a blocking-task panic as an ordinary preparation failure could hide a programming bug.                                | Preparation propagates panics. Invalid input and I/O failures use Results and stable safe codes; OS errors and input values are omitted. No panic recovery or new unsafe code is introduced.                                                                                                                  |
| M-YIELD-POINTS, M-MOCKABLE-SYSCALLS           | Interruption must work during both active traffic and a stalled stdin read.                                                    | Signal handlers are installed before input preparation. Resolution checks cancellation between rows. Active runs stop admission and await shared engine shutdown. Runtime teardown has a one-second blocking-task wait bound. Subprocess tests cover SIGINT during stdin preparation and SIGTERM during load. |
| M-MEM-REUSE, M-INITIAL-CAPACITY               | Repeated confirmation validation and retaining a resolved configuration through reporting keep unnecessary request data alive. | Preparation retains its confirmation. The CLI records only allowlisted context before transferring configuration ownership to the engine. Definitions, file reads, secret values, and prepared rows have explicit bounds.                                                                                     |
| M-STRONG-TYPES, M-UNSOUND                     | General string replacement across serialized JSON could corrupt enum values, schema keys, or decimal counters.                 | Redaction touches textual origin/identity/metadata fields only. Native verdicts and numerical evidence stay unchanged. A subprocess test checks an assertion identifier equal to a short secret.                                                                                                              |
| M-MOCKABLE-SYSCALLS, M-INTEGRATION-TESTS      | File and signal behavior needs process-level evidence, including partial failures.                                             | Tests under `crates/velo-cli/tests/` use ephemeral loopback servers, injected child environments/stdin, temporary directories, invalid destinations, and real process signals. There is no module mocking or production-only test hook.                                                                       |
| M-CARGO-WORKSPACE, M-CRATES-IN-WORKSPACE      | A `velo` CLI binary would overwrite the desktop executable in the shared target directory.                                     | The package and binary are `velo-cli`; edition, MSRV, package metadata, lint settings, and dependency versions come from the workspace.                                                                                                                                                                       |
| M-CANONICAL-DOCS, M-MODULE-DOCS, M-DOC-INLINE | Shared public APIs need explicit privacy and verdict contracts.                                                                | New public functions document arguments, results, and compiling examples. Modules describe ownership boundaries, and the engine re-export uses `doc(inline)`.                                                                                                                                                 |

No unresolved correctness or security finding remains within this scope. Application allocator and target-CPU recommendations do not justify changing the project's allocator or producing machine-specific binaries without profiling and distribution requirements. Those settings remain unchanged.

## Evidence

- CLI subprocess coverage checks preparation without traffic, exact-origin authorization, unknown definition fields, missing secrets/environments, environment and stdin inputs, shared artifacts, failed criteria, baseline budgets, dataset allocation, scenarios, output failures, redaction, and interruption.
- Shared report tests check native verdict aggregation, unavailable evidence, precision, compatibility, and JUnit outcomes.
- The TypeScript helper is tested against desktop's existing preparation function for seeded localized Faker, CSV, JSON, and safe failures.
- `cargo tree --locked -p velo-cli --edges normal` verifies host independence.
- `cargo clippy --workspace --all-targets -- -D warnings`, `RUSTDOCFLAGS='-D warnings' cargo doc --no-deps -p velo-cli -p velo-engine -p velo-contracts`, and `pnpm bindings:check` are the focused audit checks. Repository completion additionally requires `pnpm check`, `pnpm typecheck`, `pnpm test`, and `pnpm build` in that order.

The new Linux headless workflow provides a CI check without desktop system packages. Cross-platform desktop checks still exercise the adapter through the workspace test suite. No external target is contacted by tests.
