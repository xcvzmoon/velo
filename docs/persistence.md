# Persistence and credentials

Velo stores `velo.sqlite3` in Tauri's application data directory. An OS file lock gives one application instance ownership of history; another instance reports storage unavailable instead of recovering a live run. Summaries and thresholds remain until you delete their history entry. Lists use pages of 25; comparisons load at most two selected runs with matching origin, HTTP method, and workload kind. Review request settings and target conditions before drawing comparisons. Interrupted runs show their last observed measurements rather than a completed result.

Each run retains at most 600 aggregate intervals. At capacity, storage keeps every second point and doubles the sampling stride. History shows the stride explicitly; retained intervals are samples, not merged buckets. Missing intervals mark history incomplete and hide its chart. The live chart retains its existing 600-point window. There is no individual request storage or automatic summary expiry, so total disk usage grows with retained runs.

A queue holds at most 32 aggregate updates. Queue overflow never waits on execution; it marks missing history. A blocking worker writes SQLite transactions outside measurement and UI threads. Terminal publication waits up to five seconds for final persistence acknowledgement. A full queue or missed deadline reports a history write failure instead of holding up native cleanup. Storage failures appear in Results and do not change the engine's outcome. A crash can lose pending writes; startup marks unfinished records interrupted.

Saved test definitions retain non-secret literal request fields, variables, and environments in SQLite. Shared credential validation rejects literal authentication and recognized sensitive fields, including setup, journey, and cleanup steps and environment aliases, before saving or exporting. Resolved secrets stay in the OS credential store; the document contains references. Named test saves replace an existing definition with the same name. See [test authoring](authoring.md) for sharing and deletion behavior.

Earlier saved configurations remain readable through the unified authoring flow. Their default saves omitted URL paths, query values, headers, authentication, bodies, and upload paths. Re-enter these fields before running. Names are stored in SQLite; avoid secrets in names. Remembered requests stored the full configuration through [keyring](https://docs.rs/crate/keyring/3.6.0), with only a reference and redacted configuration in SQLite. Credential denial or unavailability requires re-entry, with no plaintext fallback. OS store size limits apply; Velo also rejects remembered payloads over 64 KiB. Deleting a remembered configuration atomically removes its SQLite metadata and records pending credential cleanup before contacting the OS store. Failed cleanup remains journaled and is retried at startup. Credential operations run outside the SQLite lock; unrelated requests without stored credentials remain available while credential access is busy. SQLite itself is not encrypted.

Baseline pins, release metadata, safe execution identities, and comparison settings share this SQLite database. Regression verdicts are stored separately from measured snapshots and absolute thresholds. A pin can be removed without deleting its source run. Deleting a baseline keeps dependent references unavailable instead of selecting a replacement. See [baseline comparisons and reports](reports.md) for review, budget, and export semantics.
